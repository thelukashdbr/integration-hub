# Integration Hub

A backend service that centralizes integrations with external REST APIs: register an integration (base URL, authentication type, default headers, timeout), store its credential encrypted, and — as the next increments land — execute requests through it, keep an execution history and run health checks against it.

It models the day-to-day of an Integration / API Support Engineer: credentials that must never leak, requests that time out or come back `401`, and the need to know *which* integration failed, *when*, and *why*.

This is a portfolio project, built incrementally. This README describes what exists today; the [Roadmap](#roadmap) lists what is coming next and in what order.

## Overview

The central concept is an **Integration**: an external API the hub knows how to talk to. Each integration has at most one **Credential**, which holds the secret needed to authenticate against that API.

```
Integration        (name, base_url, auth_type, default_headers, timeout_seconds, status)
  └── Credential   (API_KEY | BEARER_TOKEN; config in plain JSONB, secret encrypted with Fernet)
```

`auth_type` on the integration declares *how* it authenticates (`NONE`, `API_KEY`, `BEARER_TOKEN`, `OAUTH2_CLIENT_CREDENTIALS`). The credential provides the *value*. The two are kept consistent: a credential of the wrong type is rejected, and `auth_type` cannot change while a credential exists.

## Architecture

```
integration-hub/
├── docker-compose.yml         # postgres + api; migrations run on start
├── Dockerfile
├── pyproject.toml             # dependencies, ruff and pytest config
├── alembic/                   # migrations (autogenerated, reviewed by hand)
├── app/
│   ├── main.py                # FastAPI app, routers, exception handlers, /health
│   ├── api/                   # HTTP layer only: parse, call a service, map the status code
│   │   ├── deps.py            # DbSession, require_api_key
│   │   ├── integrations.py
│   │   └── credentials.py
│   ├── core/                  # config, logging, security (encryption), exceptions
│   ├── db/
│   │   ├── session.py         # engine, SessionLocal, Base, get_db
│   │   └── models.py          # SQLAlchemy models
│   ├── schemas/               # Pydantic request/response models
│   └── services/              # business rules; no FastAPI imports
├── scripts/create-test-db.sql
└── tests/
```

**Routes are thin; services own the rules.** A route parses input, calls one service function and maps the outcome to a status code. Everything that is a rule — name uniqueness, "this credential does not match the integration's auth type", "don't change `auth_type` while a secret is stored" — lives in `services/` and raises plain Python exceptions (`NotFoundError`, `ConflictError`). `main.py` translates those into `404`/`409`. Services never import FastAPI, so they can be exercised from tests or a future worker without an HTTP request in the way.

**Sync SQLAlchemy and sync HTTP, on purpose.** Route handlers are `def`, not `async def`; FastAPI runs them in a worker thread, so a blocking database call does not block the event loop. When request execution lands it will use `httpx.Client` for the same reason — one concurrency model per request instead of mixing a sync session with an async HTTP client.

**One credential per integration.** An integration has one way of authenticating, so the credential is a 1:1 child (`PUT` creates or replaces it) rather than a list where the code has to guess which entry to use.

**Config and secret are stored separately.** A credential has a plain `config` column (non-sensitive settings such as the API key header name) and an `encrypted_secret` column. Reads never touch the secret; only request execution will decrypt it, in memory, to build the outbound request. What counts as secret is decided in the Pydantic schema — every field typed `SecretStr` is encrypted, everything else is config — so adding a new credential type does not require touching the service.

**Operator status vs. observed health.** `Integration.status` (`ACTIVE`/`PAUSED`) is set by an operator and is never flipped by the system. Health-check results will live in their own fields when that feature lands, so "someone paused this" and "the last check failed" stay distinguishable.

**Enums are stored as `VARCHAR`, not native Postgres `ENUM` types.** Adding a value (a new `auth_type`, for instance) then needs no `ALTER TYPE` migration, and the allowed values are already enforced by Pydantic at the API boundary.

**The hub's own API requires a key.** Every route except `/health` requires an `X-API-Key` header matching `HUB_API_KEY`, compared in constant time. A service that stores credentials and will execute requests with them should not be open, even in an MVP.

## Features (current)

- Create, list (paginated, filterable by status), get, update and delete integrations
- Validate and normalize `base_url` (http/https only, no query string or fragment, lowercase host, no trailing slash)
- Reject `Authorization` in `default_headers` — that header belongs to the credential
- Store one credential per integration (`API_KEY` or `BEARER_TOKEN`), encrypted at rest, never returned or logged
- Enforce consistency between `auth_type` and the stored credential
- Health endpoint that checks real database connectivity
- Structured JSON logs
- Reproducible startup with Docker Compose (migrations applied automatically)

## Tech Stack

Python 3.14 · FastAPI · Pydantic v2 · SQLAlchemy 2.x · PostgreSQL 17 · Alembic · Pytest · HTTPX · Docker / Docker Compose · Ruff

No Redis, message broker, Celery, Kubernetes or cloud provider. The point of the project is integration fundamentals; those would add moving parts without demonstrating anything the current scope calls for.

## Getting Started

### Prerequisites

- Docker and Docker Compose

### Setup

```bash
git clone https://github.com/thelukashdbr/integration-hub.git
cd integration-hub
cp .env.example .env
```

Fill in the two secrets in `.env`:

```bash
# CREDENTIAL_ENCRYPTION_KEY — Fernet key used to encrypt credentials at rest
docker run --rm python:3.14-slim python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# HUB_API_KEY — the key clients send as X-API-Key
docker run --rm python:3.14-slim python -c "import secrets; print(secrets.token_urlsafe(32))"
```

The application refuses to start with an invalid Fernet key, so a misconfiguration surfaces immediately instead of on the first credential write.

### Running with Docker

```bash
docker compose up --build
```

| Service    | Port | Purpose                                    |
|------------|------|--------------------------------------------|
| `api`      | 8000 | Integration Hub                            |
| `postgres` | 5432 | Database (also creates the test database) |

The `api` container runs `alembic upgrade head` before starting uvicorn, so a fresh clone is usable with this single command. Interactive docs: **http://localhost:8000/docs** — click *Authorize* and paste your `HUB_API_KEY`.

### Running locally without Docker (API only)

Postgres still comes from Compose; the API runs in a virtualenv with auto-reload:

```bash
docker compose up -d postgres
python -m venv .venv && source .venv/bin/activate   # .venv\Scripts\activate on Windows
pip install -e ".[dev]"
alembic upgrade head
uvicorn app.main:app --reload
```

### Environment variables

| Variable                    | Required | Default                                   | Description                                             |
|-----------------------------|----------|-------------------------------------------|---------------------------------------------------------|
| `DATABASE_URL`              | no       | `postgresql+psycopg://…@localhost:5432/…` | SQLAlchemy URL. Compose points it at the `postgres` service |

## API Documentation

Full OpenAPI/Swagger at `/docs`. Summary:

| Method | Path                                    | Description                                              |
|--------|-----------------------------------------|----------------------------------------------------------|
| POST   | `/integrations`                         | Create an integration                                    |
| GET    | `/integrations`                         | List integrations, **paginated**, optional `?status=`    |
| GET    | `/integrations/{id}`                    | Get an integration                                       |
| PATCH  | `/integrations/{id}`                    | Partial update (any field, including `status`)           |
| DELETE | `/integrations/{id}`                    | Delete an integration and its credential                 |
| PUT    | `/integrations/{id}/credential`         | Create (`201`) or replace (`200`) the credential         |
| GET    | `/integrations/{id}/credential`         | Read credential metadata (never the secret)              |
| DELETE | `/integrations/{id}/credential`         | Delete the credential                                    |
| GET    | `/health`                               | Liveness + database connectivity (no API key required)   |

### Pagination

`GET /integrations` accepts `?limit=` (default `20`, max `100`) and `?offset=` (default `0`):

```json
{ "items": [ ... ], "limit": 20, "offset": 0, "total": 87 }
```

`total` counts every matching row, not just the page. Out-of-range values are a `422`, not silently clamped. Results are ordered by `created_at` descending with `id` as a tiebreaker, so two rows sharing a timestamp cannot swap places between pages.

## Example Flow

All requests below carry `X-API-Key: <HUB_API_KEY>`.

**1. Create an integration**

```http
POST /integrations
{
  "name": "Payments API",
  "description": "Internal payments service",
  "base_url": "https://Payments.Example.com/v1/",
  "auth_type": "API_KEY",
  "default_headers": { "Accept": "application/json" },
  "timeout_seconds": 5
}
```
```json
{
  "id": "47f476e9-…",
  "name": "Payments API",
  "base_url": "https://payments.example.com/v1",
  "auth_type": "API_KEY",
  "default_headers": { "Accept": "application/json" },
  "timeout_seconds": 5.0,
  "status": "ACTIVE",
  "created_at": "…", "updated_at": "…"
}
```

`base_url` came back normalized. Sending it again with the same `name` → `409 Conflict`.

**2. Store its credential**

```http
PUT /integrations/47f476e9-…/credential
{ "auth_type": "API_KEY", "header_name": "X-Api-Key", "api_key": "sk_live_example" }
```
```json
{
  "id": "c92e8048-…",
  "integration_id": "47f476e9-…",
  "auth_type": "API_KEY",
  "config": { "header_name": "X-Api-Key" },
  "created_at": "…", "updated_at": "…"
}
```

Response status `201`. `api_key` is not in the response, and never will be. Sending the `PUT` again replaces the secret in place and returns `200`.

For a bearer token integration the payload is `{ "auth_type": "BEARER_TOKEN", "token": "…" }`. The body is a discriminated union on `auth_type`, so Swagger shows one schema per type.

**3. Mismatches are refused, not guessed**

```http
PUT /integrations/47f476e9-…/credential
{ "auth_type": "BEARER_TOKEN", "token": "…" }
```
```json
{ "detail": "Credential type BEARER_TOKEN does not match integration auth_type API_KEY" }
```

Status `409`. The same status is returned when trying to `PATCH` `auth_type` while a credential exists — delete the credential first, then change the type.

**4. Pause it**

```http
PATCH /integrations/47f476e9-…
{ "status": "PAUSED" }
```

`PAUSED` is an operator decision; once request execution lands, a paused integration refuses to execute requests (`409`).

## Error Handling & Security

| Status | Meaning                                                                                     |
|--------|---------------------------------------------------------------------------------------------|
| 401    | Missing or invalid `X-API-Key`                                                              |
| 404    | Integration or credential not found                                                        |
| 409    | Duplicate integration name · credential type ≠ `auth_type` · `auth_type` change with a credential present |
| 422    | Request body fails validation (invalid `base_url`, `Authorization` in headers, bad payload)  |
| 503    | `/health`: database unreachable                                                             |

**Secrets.** Credential secrets are encrypted with Fernet (AES-128-CBC + HMAC, from the `cryptography` library) using `CREDENTIAL_ENCRYPTION_KEY`. Secret fields are typed `SecretStr` in the schemas, so even an accidental `repr` prints `**********`. The test suite asserts that the plaintext is absent from the database bytes, from every API response and from every log record. **Documented limitation:** the key lives in an environment variable on the API container. That is fine for a portfolio MVP; a production deployment would source it from a secrets manager (AWS KMS, Vault, Azure Key Vault) with rotation and access auditing. `.env` is git-ignored.

**No `Authorization` in configuration.** `default_headers` rejects that header: the credential is the only place a secret is allowed to live, so it cannot end up in a plain JSONB column by accident.

## Database & Migrations

Alembic reads the connection string from the same `Settings` object the app uses — there is no second copy of the URL in `alembic.ini`. Migrations are autogenerated against a real Postgres and reviewed by hand before being committed:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
alembic check          # fails if models and migrations have drifted
```

`alembic check` will run in CI so a model change without a migration fails the build rather than the deployment.

## Logging

One JSON object per line (`python-json-logger`), so fields are queryable instead of grepped out of prose:

```json
{"timestamp": "2026-09-12 17:22:59,845", "level": "INFO", "name": "app.services.credential_service", "message": "credential created", "integration_id": "3be27f89-…", "auth_type": "BEARER_TOKEN"}
```

Tokens, API keys and other secrets are never included in a log record. `httpx`'s own logger is set to `WARNING` because it logs the full URL of every outbound call at `INFO`.

## Running Tests

Tests run against a real Postgres database — `JSONB` and `UUID` are Postgres-specific, so a lighter database would exercise different code paths. The `integration_hub_test` database is created automatically by the Compose Postgres service (`scripts/create-test-db.sql`).

```bash
# inside the api container
docker compose run --rm api pytest

# or locally, with the Compose postgres running
pytest
```

Tables are created from the models at the start of the session and every table is wiped after each test. Lint and formatting:

```bash
ruff check . && ruff format --check .
```

Current coverage (33 tests): API key enforcement, database health check (including the unreachable case, asserting nothing leaks), integration CRUD with validation, normalization, pagination, filtering and `409` cases, and credentials — encryption at rest, secret absent from responses and logs, type mismatch rules, cascade on delete.

## Roadmap

Being built incrementally, in this order:

1. ~~Project foundation~~ · ~~Integrations CRUD~~ · ~~Encrypted credentials~~
2. **Request execution** — `POST /integrations/{id}/execute` with method, path, headers, query and JSON body; the credential is applied server-side; timeouts, connection errors, non-2xx responses and invalid payloads are classified, not just re-raised
3. **Execution history** — every execution recorded with method, path, status code, duration, outcome and error message; queryable per integration
4. **Health check** — `POST /integrations/{id}/health-check` distinguishing *unreachable*, *timeout*, *authentication error*, *HTTP error* and *unexpected response*
5. **OAuth 2.0 client credentials** — token endpoint, encrypted token cache with expiry-based refresh
6. **Request-id correlation in logs**, **GitHub Actions CI** (Postgres service container, ruff, `alembic check`, pytest)

Deliberately out of scope for the MVP: automatic retries with backoff, background workers, metrics/tracing, rate limiting, a secrets manager integration, and a UI.
